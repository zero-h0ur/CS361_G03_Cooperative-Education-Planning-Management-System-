# CO-ED V4 — Planning, Tracking & Reliability

**CO-ED คือระบบข้อมูลและวางแผนสหกิจศึกษา** สำหรับนักศึกษาและผู้ดูแลกระบวนการสหกิจ ช่วยให้นักศึกษาค้นหาสถานประกอบการ เตรียมข้อมูลและเอกสารสมัคร ส่งใบสมัครให้ผู้ประสานงาน และติดตามความคืบหน้าได้ในพื้นที่เดียว ส่วนผู้ประสานงานมีคิวใบสมัครและหลักฐานสำหรับตรวจสอบตามรอบที่รับผิดชอบ

โครงการพัฒนาต่อเนื่องจากเว็บไซต์ข้อมูลและรายชื่อบริษัท ไปสู่ระบบส่งแผนและใบสมัครที่แยกหน้าที่ของนักศึกษา เจ้าหน้าที่ ผู้ประสานงาน กรรมการ และอาจารย์ที่ปรึกษา รุ่นปัจจุบันคือ **V4** และยังอยู่ระหว่างพัฒนา/เปิดทดลองเฉพาะขอบเขตที่กำหนด ไม่ใช่ระบบที่เปิดใช้ครบทุกขั้นตอนแล้ว

## ทำไมจึงพัฒนาระบบนี้

การเข้าสหกิจมีมากกว่าการเลือกบริษัท นักศึกษาต้องเตรียมผลการเรียน เอกสาร และข้อมูลให้ครบ ขณะที่ผู้ดูแลต้องรู้ว่าใครส่งแล้ว ส่งฉบับไหน และรายการใดอยู่ในความรับผิดชอบของตน เป้าหมายของ CO-ED คือทำให้ขั้นตอนเหล่านี้เชื่อมต่อกันและตรวจสอบย้อนหลังได้

- **สำหรับนักศึกษา:** มีจุดเตรียมและส่งใบสมัคร พร้อมหลักฐานว่าระบบรับข้อมูลและส่งเข้าคิวผู้ประสานงานแล้ว
- **สำหรับผู้ดูแล:** เห็นใบสมัครและเอกสารฉบับเดียวกับที่นักศึกษาส่ง จัดการช่วงรับสมัคร และตรวจเฉพาะรายการที่ได้รับมอบหมาย
- **สำหรับกระบวนการสหกิจ:** แยกการสมัครเข้าแผน การพิจารณาคุณสมบัติ และการตอบรับจากบริษัทออกจากกัน เพื่อไม่ให้สถานะหนึ่งถูกเข้าใจว่าเป็นผลสำเร็จของทุกขั้นตอน

ระบบช่วยรวบรวมข้อมูลและแสดงความคืบหน้า แต่ **ไม่ตัดสินผลคัดเลือกแทนผู้รับผิดชอบ** ข้อมูลการศึกษาที่นักศึกษากรอกเองยังต้องได้รับการตรวจสอบจากหลักฐาน

## ขอบเขตของ source ปัจจุบัน

ระบบแบ่งหน้าที่เพื่อให้แต่ละฝ่ายเห็นและจัดการเฉพาะข้อมูลที่รับผิดชอบ ตารางนี้อธิบายบทบาทโดยรวม ส่วนที่เปิดใช้จริงในรอบทดลองเป็นไปตามสถานะด้านบน

| ผู้ใช้ | การใช้งาน |
| --- | --- |
| Public | ค้นหาและดูชื่อ ที่ตั้ง และโลโก้บริษัทได้ รายละเอียดตำแหน่งและประกาศจริงต้องเข้าสู่ระบบ ไม่มีสิทธิ์เข้าถึงข้อมูลนักศึกษาหรือแผน |
| Student | ตรวจข้อมูลของตน เตรียมใบสมัคร บันทึกร่าง แนบหลักฐาน ส่งเข้าคิว และดูความคืบหน้า; แผนบริษัทเดิมอยู่แยกจากใบสมัครเข้าแผน |
| Staff | ค้นหาและตรวจแผนในขอบเขตภาควิชา/หลักสูตร/ปีการศึกษาที่รับผิดชอบ กำหนดเอกสาร ส่งกลับแก้ไข อนุมัติหรือปฏิเสธ มอบหมาย Advisor และบันทึกผลยืนยันจากบริษัท |

นักศึกษาเข้าสู่ระบบด้วยบัญชี TU ส่วนผู้ประสานงาน กรรมการ และเจ้าหน้าที่ใช้บัญชี Cognito ที่จัดเตรียมไว้ การเข้าสู่ระบบเพียงอย่างเดียวไม่ทำให้เห็นข้อมูลของทุกคน ระบบยังตรวจเจ้าของข้อมูลและการมอบหมายหน้าที่ก่อนอนุญาตให้ใช้งาน

## เส้นทางใบสมัคร Phase 1

ใบสมัคร Phase 1 คือ **การสมัครเข้าแผนสหกิจ** ไม่ใช่การสมัครงานกับบริษัทโดยตรง:

1. นักศึกษาเข้าสู่ระบบด้วย TU และยืนยันข้อมูลเพิ่มเติมในการเข้าใช้ครั้งแรก
2. เลือกรอบรับสมัคร กรอกข้อมูลและผลการเรียน แล้วบันทึกฉบับร่างได้
3. แนบ Resume/CV, Transcript, รูปนักศึกษา และใบรับรองความประพฤติ
4. ตรวจข้อมูลและคำรับรองคุณสมบัติ ก่อนยืนยันส่งด้วยตนเอง
5. ระบบเก็บใบสมัครฉบับที่ส่งพร้อมหลักฐานปลายทาง ให้ผู้ประสานงานที่รับผิดชอบเห็นฉบับเดียวกัน

**“ส่งเข้าคิวแล้ว” ไม่ได้แปลว่า “ผ่านคุณสมบัติ” หรือ “ได้รับคัดเลือกแล้ว”** หลักสูตร/กลุ่มวิชาและข้อมูลที่นักศึกษาแจ้งเองแสดงเป็นรอตรวจสอบ หากข้อมูลคำนวณเกรดยังไม่ยืนยัน ระบบไม่สรุปว่าผ่านแทนผู้ตรวจ

ผู้ประสานงานเลือกรับสมัครตามวันเวลา หรือเปิดจนกดปิดได้เฉพาะรอบที่รับผิดชอบ เมื่อปิดรับจะหยุดการสร้าง แก้ไข แนบไฟล์ และส่งฉบับร่างทั่วไป แต่ยังอ่านข้อมูลเดิมได้ ส่วนใบสมัครที่ถูกส่งกลับแก้ไขใช้กำหนดเวลาพิจารณาเดิม โดยขั้นตอนส่งกลับยังไม่เปิดในรอบทดลองปัจจุบัน

## แผนบริษัทเดิม — Legacy V3

ส่วนนี้เก็บอธิบายระบบเดิม ไม่ใช่สถานะใบสมัคร Phase 1 หรือ workflow ที่เปิดทั้งหมดใน pilot:

นักศึกษาตรวจข้อมูลของตน เลือกรอบสมัคร ระบุบริษัท ตำแหน่งและ Project ที่สนใจ แล้วส่งแผนพร้อมเลขอ้างอิงหรือลิงก์เอกสารตามข้อกำหนดของ Staff เจ้าหน้าที่ตรวจแผนในขอบเขตที่รับผิดชอบ โดยคิวรอตรวจเรียงตามเวลาส่งแบบเก่าก่อน

```text
DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED
                         ├──────→ REJECTED
                         └──────→ NEEDS_REVISION → SUBMITTED
DRAFT → CANCELLED
```

- `NEEDS_REVISION`: Staff ระบุเหตุผล นักศึกษาเจ้าของแผนแก้แล้วส่งใหม่ได้ แต่ยกเลิกไม่ได้
- `REJECTED`: ไม่ผ่านเกณฑ์ เป็นสถานะสิ้นสุดในรอบนั้น แก้หรือยื่นซ้ำในรอบเดิมไม่ได้
- `CANCELLED`: ยกเลิกแบบเก็บประวัติได้จาก `DRAFT` เท่านั้น ไม่ลบแถวข้อมูลออกจากฐานข้อมูล

เมื่อแผน `APPROVED` แล้ว Staff จึงมอบหมาย Advisor ได้ โดยจำกัดการดูแลพร้อมกันไม่เกิน 5 คนต่อ Advisor ส่วนผลตอบรับบริษัทบันทึกใน Placement แยกจากแผน **ผ่านเกณฑ์สหกิจไม่ได้แปลว่าบริษัทตอบรับแล้ว** Staff ต้องตรวจบริษัทและรหัสนักศึกษาให้ตรงกับหลักฐานที่ได้รับ

Backend ตรวจ role, ownership, scope, state และ version ก่อนเปลี่ยนข้อมูล ใช้ operation ID ป้องกันการทำรายการซ้ำ และบันทึกผลพร้อม audit ใน transaction เดียวกัน

### เหตุผลสำคัญในการออกแบบ

- **แยกตัวตนออกจากหน้าที่:** TU ยืนยันว่าเป็นใคร แต่สิทธิ์ดูและตรวจใบสมัครขึ้นกับบัญชีภายในและการมอบหมาย ไม่ใช่แค่ Login ผ่าน
- **แยกใบสมัครเข้าแผนออกจากแผนบริษัท:** การผ่านเกณฑ์สหกิจไม่เท่ากับบริษัทตอบรับ จึงไม่ใช้สถานะเดียวแทนทั้งสองเรื่อง
- **เก็บฉบับที่ส่งและประวัติไว้:** ผู้ตรวจต้องเห็นหลักฐานเดียวกับที่นักศึกษาส่ง และตรวจย้อนหลังได้ ไม่ให้การแก้ข้อมูลภายหลังเปลี่ยนฉบับเดิมเงียบ ๆ
- **ไม่รับรองข้อมูลที่ยังไม่ยืนยัน:** ข้อมูลที่กรอกเองและเกณฑ์ที่ยังไม่ครบต้องรอตรวจ ไม่สร้างข้อมูลสมมติเพื่อให้ระบบประกาศว่าผ่าน
- **เก็บฐานข้อมูลและเอกสารเป็นส่วนตัว:** Browser ไม่เชื่อม RDS โดยตรงและไม่ได้รับรหัสฐานข้อมูล ส่วนไฟล์มีสิทธิ์เข้าถึงแยกจากหน้า public

รายละเอียด TU broker/issuer, ขอบเขตการตรวจสิทธิ์ และเส้นทางใบสมัครอยู่ใน [V4 architecture](docs/architecture/G03-V4-architecture.md) พร้อม [เหตุผลและข้อแลกเปลี่ยน](docs/decisions/README.md)

## เริ่มพัฒนา

ทีม V4 เริ่มจาก [คู่มือ Dev/Test](docs/operations/team-dev-test.md) มีคำสั่งเตรียม PostgreSQL, fixtures, local API และ Tests
ทุกคนทำได้ครบส่วนของงานที่รับ ส่วน [สิทธิ์ทีมและบัญชีเว็บ](docs/operations/team-access.md) จัดแยกจากบทบาทในโปรแกรม

ใช้ Node.js 22 ตาม `.nvmrc` และ npm:

```bash
npm ci
npm run dev:ui
```

เปิด [Local UI](http://localhost:8081/app.html#/student/plan) เพื่อดูหน้าจอด้วยข้อมูลจำลองใน memory ไม่ต้องใช้ AWS หรือฐานข้อมูล Preview เปลี่ยน role และสถานการณ์เพื่อดูหน้าจอได้ แต่ไม่ใช่การทดสอบ Login หรือสิทธิ์จริง ดูรายละเอียดใน [Local UI Preview](docs/frontend/local-ui-preview.md)

หากต้องใช้ API หรือ PostgreSQL ให้ตั้งฐานข้อมูล development และ test คนละตัวตาม [Team Dev/Test](docs/operations/team-dev-test.md) และ [intake verification](docs/operations/student-intake-verification.md) ห้ามใช้ RDS เป็นฐานข้อมูลทดสอบ

```bash
npm run lint
npm run test:frontend
npm run test:ui-preview
npm run test:docs
```

Full regression ใช้ `npm test` หลังเตรียมฐานทดสอบแยกที่ล้างข้อมูลได้ตาม [วิธีทดสอบ](docs/operations/student-intake-verification.md) และ [CI workflow](.github/workflows/v4-verification.yml) บางชุดต้องตั้งค่าฐานเพิ่มเติมจากตัวช่วย local เดิม การ skipped ไม่ถือว่าผ่าน integration และห้ามใช้ RDS เป็นฐานทดสอบ

`npm start` เปิด local API; วิธีเตรียม session/ข้อมูลจำลองอยู่ในคู่มือ Dev/Test ส่วน `npm run build:v4` สร้าง frontend ใน `dist/` ด้วย [public configuration](config/v4-public.json) โดยไม่ต้อง Login AWS ไม่ใส่รหัสผ่านหรือ AWS credentials ใน Browser

การ build เป็นการเตรียมไฟล์ในเครื่อง ไม่ Deploy หรือเปลี่ยนฐานข้อมูลอัตโนมัติ

## ข้อจำกัดและงานต่อ V4

### ใบสมัคร Phase 1 (#141)

ผู้ใช้ในรอบทดลองยืนยันเส้นทางกรอก → ร่าง → แนบไฟล์ → ส่ง → ผู้ประสานงานเห็นใบเดียวกันและดาวน์โหลดชื่อไฟล์เดิมได้แล้ว แต่ยังไม่ใช่การตรวจรับทั้งระบบ ดู [ผลทดสอบและสิ่งที่ยังไม่ยืนยัน](docs/operations/student-intake-verification.md)

ยังไม่มีข้อมูลหน่วยกิตและกติกาเรียนซ้ำที่ยืนยันครบ จึงรับหลักฐานที่ครบเข้าคิวรอตรวจโดยไม่รับรองว่าผ่าน เกณฑ์ต้นทางปี 2568 ที่ทีมใช้ศึกษาไม่ใช่ประกาศรับรองปี 2569 หรือข้อมูลการศึกษาทางการของผู้สมัคร

การรับเรื่อง ส่งกลับ ส่งต่อ และการคัดเลือกปลายทางยังไม่เปิดในรอบทดลอง แม้มีโค้ดหรือ tests อยู่ และผลทดสอบ Preview ไม่แทนการใช้บัญชี/ไฟล์จริง

### ระบบเดิมและงานที่ยังไม่รวม

- หลักฐานจำลองช่วงย้าย V4 เคยครอบคลุมเส้นทางถึงกรรมการ 3 คน แต่ไม่ใช่การตรวจรับ Phase 1 Ranking หรือการเปิด Committee ใน pilot ปัจจุบัน และยังไม่ครอบคลุมทุก role/เส้นทาง/การประกาศผลจริง
- เส้นทางรับแผน/ความเห็นรายคนของรุ่นเดิมยังเก็บไว้แยกจาก Phase 1 เพื่อความเข้ากันได้ ไม่ใช่กติกา Ranking ของหน้าจอใหม่ ดู [ประวัติขอบเขตการคัดเลือกเดิม](docs/operations/selection-workflow.md) และ [ขอบเขต Coordinator รุ่นใหม่](docs/evidence/coordinator-workspace-redesign.md)
- เชื่อม TU เพื่อยืนยันตัวตนแล้ว แต่ไม่ใช่ระบบทะเบียน/Transcript ที่ยืนยันหลักสูตร กลุ่มวิชา หน่วยกิตและกติกาเรียนซ้ำครบ จึงไม่จัดอันดับหรือตัดสินผลอัตโนมัติจากข้อมูลที่กรอกเอง
- เอกสารของ V3 ยังเป็นลิงก์หรือเลขอ้างอิงภายนอก ไม่เปลี่ยนเป็นไฟล์จริงอัตโนมัติ; ไฟล์จริงใช้เฉพาะโดเมนใบสมัคร Phase 1 ใหม่
- Logout ล้าง session ข้ามแท็บและเรียกเพิกถอน refresh token แต่ยังไม่รับประกันการปฏิเสธ Access Token เดิมทันทีที่ API; token ที่ตรวจด้วยลายเซ็นอาจใช้ได้จนหมดอายุ
- Admin ยังไม่มีหน้าจัดการบริษัทหรือเปลี่ยนบัญชีผ่านเว็บโดยตรง การส่งอีเมล/แจ้งเตือนภายนอกอัตโนมัติและการเชื่อมทะเบียนแบบเต็มยังไม่ได้ตรวจรับใน pilot
- V4 ต้องทบทวน requirement, workflow และหน้าจอของแต่ละ role ใหม่ ไม่ถือว่ากติกาใน V3 เป็นข้อกำหนดสุดท้าย รายการด้าน deployment, session และ logging อยู่ใน [คู่มือส่งต่อ](docs/operations/v3-operating-guide.md#งานต่อ-v4)
